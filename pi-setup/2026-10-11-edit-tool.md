# 2026-10-11 — apply_patch → pi's own edit / write

## Decision

`apply_patch` (2,135 lines + 2,525 test lines, four call shapes) is gone.
`edit` and `write` are pi's own tools (`createEditToolDefinition` /
`createWriteToolDefinition`), registered under pi's names from
`extensions/tools/edit-write.ts` with injected file `operations`. The wrapper
adds only:

| Added | Why |
|---|---|
| undo records via `file-tracker` | `undo_edit` 140 and `redo_edit` 45 calls in history; pi records nothing |
| record first, then write | a change undo cannot reach is never made, so nothing ever needs deleting |
| `permissions.json` check (`edit` / `write`) | pi is YOLO by design |
| `lib/mutex.ts` | shared with bash, `format_file` (794 calls) and undo |
| Claude names in `prepareArguments` | `file_path`, `old_string`/`new_string`, `old_str`/`new_str` |
| closest-line hint on not-found | carried by 201 of 300 recent not-found errors |
| duplicate line numbers + "no replace_all" | `replace_all` was used in 69 of 28,060 calls |
| "identical — the edit is done" | the misleading no-op message caused a 14-error streak |
| identical `write` is a success, not written | 12 identical writes errored before |

Everything else — schema, descriptions, guidelines, `constrainedSampling`,
matching, BOM/CRLF, the write — is upstream's and changes with pi updates.

## The data (all pi transcripts, 4,628 files, excluding /private/tmp)

| | calls | error rate |
|---|---|---|
| apply_patch all time | 37,191 | 4.1% |
| apply_patch since 2026-08-12 (`edit-scoreboard.py`) | 28,037 | 3.5% |
| … `old_string` lane | 16,673 | 2.1% |
| … `content` lane | 4,785 | 2.0% |
| … `ops` batch | 3,494 | 6.8% |
| … envelope | 2,977 | 9.6% |
| old `edit` tool (2025-09 → 2026-07, errors counted by text) | 23,512 | ≥2.0% |

The envelope is OpenAI's V4A format: codex constrains it with a Lark grammar,
opencode shows it only to `gpt-*` models. Claude and DeepSeek were never trained
on it. gpt-6-astra: 70 calls, 0 errors; sonnet-5-5: 9.3%.

## What the others do

- **pi**: `edit {path, edits[{oldText,newText}]}` matched against the original,
  exact → NFKC/trailing-space fuzzy; `write {path, content}`. No undo.
- **opencode**: edit + write for everyone, `patch` only for gpt. Cut a 9-matcher
  fuzzy chain to 3 tiers after destructive matches (#30932, #39258). Deleted
  read-before-write (#22999) and `multiedit` (#23701). Patch is not atomic.
- **codex**: `apply_patch` only, as a grammar-constrained freeform tool;
  first match wins; not atomic across files.

## Lost on purpose

Multi-file atomic batches, delete and move inside the edit tool (82 of 37,191
calls), `replace_all`, the leading-whitespace fuzzy tier and reindent logic,
symlink refusal. Deletes are `trash <path>` and renames `git mv`, in bash; undo
does not cover them. Every way to really delete (rm, rmdir, unlink, shred,
`find -delete`, `git rm`, `git clean`, delete calls in scripts) is blocked by
`permissions.json`, and undoing a file creation moves it to the Trash.

## Measuring (phase 4)

After a week of use:

```bash
python3 pi-setup/edit-scoreboard.py --since 2026-10-11
```

Targets: edit + write at or under 2.1%; sonnet-5-5 under 9.3%; deepseek-flash
under 5.1%; zero `call shape` and `patch format` errors.

## When to add something back (phase 5 — only on data)

- GPT models enabled again → an envelope-only `apply_patch` (restore
  `lib/codex-patch.ts` from git) shown only when the model id contains `gpt-`,
  opencode's gate.
- `whitespace or line breaks differ` above ~5% of not-found errors → one
  leading-whitespace tier, unique matches only.
- The same model repeating an identical failing call despite the new messages →
  a per-session repeat counter (reminder at 3, refuse at 5).

## Rollback

Every change is in one commit; `git revert` it and re-run `install.sh`.
